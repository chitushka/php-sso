# План доведения SSO PHP до production-ready

## Порядок выполнения и правила закрытия

План актуализирован 4 ноября 2026 года по PHP-коду, Docker-конфигурации, миграциям, OpenAPI, тестам и эксплуатационной документации. Здесь хранится только незавершённая и явно отложенная работа. Наличие реализации или теста само по себе не подтверждает production-готовность: полный CI, нагрузочные испытания и восстановление нужно выполнить для конкретного релизного артефакта.

- Выполнять шаги по порядку: P0 — блокеры безопасности и развёртывания; P1 — обязательная функциональная и эксплуатационная готовность; P2 — сопровождаемость и окончательная приёмка. Указанные зависимости определяют порядок связанных работ.
- Для каждого шага назначить ответственного, оценить трудозатраты после уточнения решения и приложить к ревью воспроизводимые результаты проверок. Завершённые пункты удалять из этого файла.
- Для security/functional изменений проверять успех, ошибочные данные, отсутствие прав, replay и конкуренцию там, где применимо; для транзакций — откат при отказе обязательного побочного действия.
- Все проверки выполнять в Docker с явным `SSO_ENV=test` и отдельной тестовой БД. Production fail-closed проверки не ослаблять, production credentials в CI не использовать.
- Изменения поведения отражать в `ARCHITECTURE.md`, OpenAPI и contract tests; настройки, команды и регламенты — в `README.md` и `.env.example`. Новые корневые документы не создавать.
- Опираться только на PHP-приложение, его контракт и стандарты. Историческая совместимость не является требованием. Новые зависимости добавлять с обоснованием необходимости и сопровождения.

## P0 — закрыть до подключения production-трафика

### 1. Защитить первичную инициализацию администратора

Основание: `BootstrapController::actionCreate()` и `BootstrapService::createAdmin()` создают первого администратора без отдельного секрета оператора; проверяется отсутствие любых пользователей. В `ARCHITECTURE.md` условие доступности bootstrap описано иначе — через отсутствие эффективного администратора.

- [ ] Реализовать production-bootstrap через CLI либо одноразовый секрет оператора из `*_FILE`; запретить создание администратора без подтверждения владения установкой.
- [ ] Зафиксировать единое условие завершённой инициализации, не допускающее повторного открытия bootstrap после удаления/блокировки пользователей. Восстановление административного доступа вынести в отдельную операторскую процедуру.
- [ ] Сохранить advisory lock и атомарность создания пользователя, назначения роли и аудита; исключить секрет из URL, ответов и логов.
- [ ] Проверить два конкурентных bootstrap, неверный/отсутствующий секрет, повторный запуск и rollback при отказе аудита; согласовать UI, status endpoint и документацию.

Критерий: посторонний клиент не может захватить новую установку или повторно открыть bootstrap; recovery требует полномочий оператора.

### 2. Довести federation broker до полноценного OIDC Relying Party

Основание: `BrokerService::fetchIdentity()` доверяет UserInfo по полученному access token, не проверяет ID Token и допускает `id` вместо `sub`; provider не содержит issuer/JWKS. `start()` не отправляет nonce и PKCE.

- [ ] Добавить доверенный issuer, источник JWKS/metadata и разрешённые алгоритмы в модель, API, UI и схему БД. Discovery/JWKS загружать через SSRF-защиту с ограничениями размера, времени, redirect и кешированием.
- [ ] Проверять подпись ID Token, `iss`, `aud`, `azp` при применимости, временные claims и nonce; требовать OIDC `sub`, сверять его с UserInfo, отказаться от OAuth-only fallback внутри типа `oidc`.
- [ ] Хранить nonce и PKCE verifier в серверном одноразовом контексте, передавать S256 challenge/verifier; сохранить browser binding и атомарное потребление state.
- [ ] Предусмотреть обновление JWKS при неизвестном `kid`, смену конфигурации provider во время входа и безопасный отказ при недоступности ключей.
- [ ] Расширить mock IdP и HTTP-тесты: поддельная подпись, неверные issuer/audience/nonce/subject, истёкший token, смена ключа, mix-up, replay и конкурентные callback.

Критерий: федеративная сессия создаётся только после проверки OIDC identity; невалидный ответ не создаёт пользователя, link или сессию. Шаг 3 обязателен до включения федерации в production.

### 3. Применять единую MFA-политику ко всем способам входа

Основание: `AuthService::login()` проверяет `mfa_enabled`, а `issueFederatedLogin()` напрямую вызывает выдачу сессии. Recent authentication для MFA уже реализована, но обязательная MFA-политика для администраторов не задана.

- [ ] Провести local, LDAP и federation через общую финализацию входа; при локальном MFA не выдавать полноценные cookie/JWT до завершения challenge.
- [ ] Добавить обязательный MFA для административных ролей и ограниченный enrollment-контекст до настройки фактора. Делегированное MFA доверять только по явно заданной и проверенной политике `acr`/`amr` конкретного IdP.
- [ ] Закрыть гонку `createEnrollmentSecret()` с enable/disable: setup не должен сбрасывать уже включённый фактор; сохранять состояние под блокировкой с повторной проверкой условий.
- [ ] Описать recovery при потере всех факторов с отдельными полномочиями, аудитом и отзывом credentials; password reset не должен отключать MFA.
- [ ] Покрыть федеративный вход с MFA, обязательный enrollment, повтор challenge/recovery code, конкурентные setup/enable и изменение политики при активной сессии.

Критерий: ни один способ входа или восстановления не обходит MFA-политику; существующие replay-guards и отзыв credentials сохранены.

### 4. Исправить OIDC authentication context и интерактивный authorization flow

Основание: `OAuthService::authorize()` не обрабатывает `prompt`/`max_age` и возвращает `login_required`/`consent_required` без интерактивного продолжения; в ID Token передаётся время создания authorization code, а при refresh — предыдущего refresh token.

- [ ] Сохранять исходные `auth_time`, способ входа и уровень MFA в сессии, authorization code и refresh family; обновление токенов не считать повторной аутентификацией.
- [ ] Реализовать применимую семантику `prompt=none/login/consent`, `max_age`, проверку комбинаций и точные ошибки; неподдерживаемые возможности не объявлять в Discovery.
- [ ] Сделать продолжение authorize через login/MFA/consent UI: запрос хранить на сервере, привязать к браузеру и TTL, после продолжения повторно проверять client, scopes, redirect URI и PKCE.
- [ ] Проверить старую SSO-сессию, принудительный вход, silent auth без сессии/consent, отмену consent, несколько вкладок и неизменность `auth_time` во всей refresh family.

Критерий: обычный RP завершает вход через браузер без ручного предварительного логина в админку; `auth_time` отражает фактическую аутентификацию. Зависимости: шаги 2–3.

### 5. Сделать LDAP provisioning и синхронизацию прав атомарными

Основание: `LdapService` выбирает первый enabled provider по времени создания; сохранение пользователя, удаление/назначение LDAP-групп и audit выполняются без общей транзакции.

- [ ] Зафиксировать модель выбора LDAP provider: один активный каталог с валидацией либо явная маршрутизация по домену/провайдеру. Исключить неявный выбор по `created_at`.
- [ ] Объединить provisioning/update пользователя, LDAP memberships и обязательный audit в транзакцию; сериализовать синхронизацию пользователя и соблюдать инвариант последнего администратора.
- [ ] Определить стабильный LDAP identity и поведение при rename DN/login, смене email, коллизии с local/federated account и переносе между каталогами.
- [ ] Сохранить ручные memberships; проверить rollback после удаления старых групп, отказ аудита, параллельные входы, исчезновение LDAP-группы и блокировку пользователя.
- [ ] Добавить TLS/StartTLS fixture с проверкой неверного CA/hostname, запрета downgrade и времени поиска; текущий LDAP fixture использует незашифрованный bind в тестовом режиме.

Критерий: отказ LDAP/БД не оставляет частично обновлённые права, identity выбирается однозначно, production LDAP проходит проверку TLS.

### 6. Подготовить воспроизводимую production-конфигурацию TLS, secrets и БД

Основание: `tls-init` генерирует один self-signed ключ для HTTPS и PostgreSQL; общий `tls_data` монтируется в app. `.env.example` ссылается на `/run/secrets`, но базовый Compose не задаёт эти mounts; migrate/cleanup имеют иной набор mounts, чем app. `POSTGRES_USER` используется и для инициализации БД, и в примере подключения приложения.

- [ ] Вынести локальные сертификаты в development-конфигурацию; разделить HTTPS и PostgreSQL key material, CA и права чтения. App должен получать CA, а не приватный ключ сервера БД.
- [ ] Добавить production override/пример secrets mounts для app, migrate, cleanup и deployment checks; обеспечить доступность CA и `*_FILE` без записи secrets в image.
- [ ] Разделить database owner/migrator, runtime и backup roles; runtime запретить superuser, CREATE/DROP, изменение схемы и доступ к чужим БД. Проверить все use cases с минимальными правами.
- [ ] Ограничить изменение audit для runtime в рамках принятой модели; выделить полномочия retention cleanup и восстановления.
- [ ] Проверить чистый production-запуск, миграции, cleanup, deployment-check, ротацию и истечение сертификатов с `verify-full`; smoke выполнять с доверенным CA без `TLS_INSECURE`.

Критерий: установка по `README.md` работает с реальными сертификатами и файловыми secrets во всех операционных контейнерах, без default credentials и лишних привилегий.

### 7. Исключить локальные секреты из build context и артефактов

Основание: `.dockerignore` исключает `.env`, но не `.env.*`; test-stage использует `COPY . .`. Secret scan и отделение production stage уже есть, их нужно дополнить проверкой контекста.

- [ ] Исключить локальные env-файлы, private keys, dumps, credentials и служебные artifacts из контекста, сохранив безопасные examples/fixtures.
- [ ] Проверять содержимое и слои production/test images искусственным canary secret; test image также считать потенциально публикуемым артефактом.
- [ ] Распространить secret scan на изменения и релизные artifacts; описать отзыв и ротацию при подтверждённой утечке.

Критерий: canary secret не попадает в контекст, слои, SBOM, CI-логи и опубликованные artifacts.

## P1 — функциональная надёжность и эксплуатация

### 8. Закрыть гонки lifecycle и транзакционность account-операций

Основание: `AccountService::updateProfile()` сохраняет профиль до audit без общей транзакции; `changePassword()` проверяет старый пароль до транзакции; reset не инвалидирует остальные действующие password-reset ссылки.

- [ ] Сделать profile mutation и обязательный audit атомарными; унифицировать principal и безопасную обработку ошибок.
- [ ] Проверять актуальные status/source/password version под блокировкой при change/reset/verify; сериализовать операции с admin update, блокировкой и удалением пользователя.
- [ ] После смены/сброса пароля инвалидировать остальные reset grants; зафиксировать правила повторной отправки и привязки verification к текущему email, сохранив существующее удаление verification tokens при admin email update.
- [ ] Проверить точность `tokens_invalid_before` на границах секунды и гонки issuance/revocation, чтобы токен после блокировки/смены пароля не восстанавливал доступ.
- [ ] Добавить гонки двух смен пароля, reset против блокировки/смены email, replay старой ссылки и fault injection аудита/БД.

Критерий: операция проверяет актуальное состояние, старые credentials/recovery-ссылки не восстанавливают доступ, rollback не оставляет частичные изменения.

### 9. Сделать email recovery надёжным и устойчивым к enumeration

Основание: `AccountService` фиксирует token до синхронного SMTP-вызова; `forgotPassword()` игнорирует результат отправки, повторная доставка не предусмотрена.

- [ ] Добавить транзакционный outbox и worker с ограниченными retry/backoff, сроком доставки и очисткой. Секретные ссылки в outbox шифровать, ограничить доступ и TTL.
- [ ] Сохранить одинаковые ответы для неизвестного/неактивного/внешнего пользователя; проверить утечки через timing, SMTP-задержки и различие ошибок.
- [ ] Добавить лимиты по аккаунту/получателю наряду с IP, защиту от массовой рассылки и UI повторной отправки.
- [ ] Проверить остановку worker после отправки до acknowledgement, SMTP-отказы, истечение/отзыв token до отправки и запрет plaintext SMTP для внешней production-доставки.

Критерий: временный SMTP-сбой не теряет запрос, повторное выполнение безопасно, возраст очереди и окончательные отказы наблюдаемы. Зависимости: шаги 6 и 8.

### 10. Уточнить session lifetime, revocation и глобальный logout

Основание: сессии имеют абсолютный TTL без idle timeout; back-channel отправляется синхронно однократно и только клиенту из `id_token_hint`, без учёта остальных RP сессии.

- [ ] Ввести idle/absolute timeout, строгий профиль для администраторов и максимальный lifetime refresh family; rotation не должна продлевать family бесконечно.
- [ ] Зафиксировать logout current/all, отзыв consent и глобальный SSO logout, включая срок принятия ранее выданного access token внешним resource server.
- [ ] Хранить связь SSO session с RP, исходным auth context и `sid` при выбранном профиле; уведомлять все затронутые RP через надёжную очередь после локальной транзакции.
- [ ] Проверять back-channel response, ограничивать retries/время, исключить зависимость локального logout от доступности RP; описать обработку дубликатов на стороне RP.
- [ ] Проверить несколько RP/browser sessions, недоступный RP, повтор logout token, revoked consent и гонку refresh/logout.

Критерий: отзыв имеет явный проверенный контракт, глобальный выход охватывает все заявленные RP, отказ одного RP не блокирует локальный выход. Зависимости: шаги 4 и 9.

### 11. Подтвердить защиту от перебора и истощения ресурсов

Основание: route limits используют route/IP, Argon2id выполняется синхронно с фиксированной стоимостью; bucket хранится две минуты независимо от refill.

- [ ] Проверить account/IP/client/provider limits для login, MFA, reset, broker и token endpoints; учесть NAT, распределённый перебор, lockout abuse и недоверенные forwarded headers.
- [ ] Согласовать TTL bucket с capacity/refill и cleanup, чтобы удаление ещё не восстановленного bucket не обнуляло лимит; проверить минимально разрешённые настройки.
- [ ] Добавить ingress-limit на соединения/тело/время запроса и бюджет дорогих операций; измерить Argon2id под нагрузкой и обеспечить безопасный rehash при обновлении параметров.
- [ ] Проверить password policy для Unicode, длинных вводов и распространённых скомпрометированных паролей; выбрать локальный blocklist без передачи plaintext password внешнему сервису.
- [ ] Измерить различимость неизвестного пользователя и неверного пароля; добавить защиту, не создающую дополнительный DoS.

Критерий: опубликованы проверенные limits и бюджеты; публичные endpoints не позволяют исчерпать FPM/DB и не раскрывают аккаунты через очевидные различия ответа.

### 12. Подтвердить совместимость OAuth/OIDC независимыми проверками

- [ ] После шагов 2–4 и 10 составить матрицу профиля: Code + S256, public/confidential clients, refresh, client credentials, Discovery, JWKS, UserInfo, consent и logout.
- [ ] Проверить профиль независимым OIDC conformance suite и двумя RP-библиотеками; добавить запуск в Docker и устранить применимые failures.
- [ ] Расширить HTTP negative tests на повторные/неоднозначные параметры, Content-Type, client authentication, scopes, cache headers, ошибки redirect и `WWW-Authenticate`.
- [ ] Проверить минимизацию claims по scopes и отсутствие переноса произвольных profile attributes в права/claims без явного mapping.
- [ ] Сверить Discovery/OpenAPI с фактическими возможностями; ограничения на state/nonce описать как профиль. Не заявлять сертификацию без отдельной процедуры.

Критерий: воспроизводимый отчёт conformance и RP interoperability не содержит необработанных ошибок для заявленного профиля.

### 13. Подготовить процесс поставки и отката релиза

Основание: quality workflow проверяет локальный `latest`, генерирует SBOM и сканирует app image; публикация, подпись, promotion и проверка того же digest при deployment не определены.

- [ ] Закрепить Actions по SHA, base images по digest и версии PECL/browser tooling; автоматизировать контролируемые обновления. Учесть изменяемые apt-репозитории при требованиях к воспроизводимости.
- [ ] Выпускать app/web одной согласованной версией с commit SHA, digest, SBOM и provenance; сканировать все production images, подписывать и проверять артефакты перед deployment.
- [ ] Проверять Composer dev dependencies и browser npm lock; добавить расписание audit/rebuild и сроки исправления уязвимостей. Исключения scanner ограничивать по времени.
- [ ] Автоматизировать preflight → maintenance/drain → backup → single migrator → deployment-check → smoke → возврат трафика. Не выполнять миграции конкурентно с writers.
- [ ] Разделить rollback приложения и восстановление схемы/данных; описать, какие изменения допускают откат версии, а какие требуют restore. Проверять предыдущий поддерживаемый релиз и целевой артефакт на staging.
- [ ] Сохранять отчёты тестов/coverage/scan и digest в CI, включая падения; подтвердить обязательность quality gate настройками защищённой ветки.

Критерий: в production продвигается проверенный digest, релиз и откат воспроизводимы. Зависимости: шаги 6–7.

### 14. Превратить backup-рекомендации в проверенную систему восстановления

Основание: `test-backup-restore.sh` проверяет ephemeral dump и структуру/счётчики, но не обеспечивает расписание, внешнее хранение, восстановление secrets и функциональный вход после restore.

- [ ] Автоматизировать зашифрованные копии с внешним fault domain, retention, checksum и alert; RPO ≤ 24 часов и RTO ≤ 4 часов из `README.md` подтвердить замерами.
- [ ] Хранить отдельно восстанавливаемые версии encryption/JWT keys, сертификаты и конфигурацию с привязкой к схеме/образу; восстановление БД без ключей считать неуспешным.
- [ ] Выполнять изолированный drill: поднять приложение, проверить DB invariants, decrypt/signing round trip, login/MFA, OAuth и provider credentials через безопасные fixtures.
- [ ] Предотвратить оживление отозванных сессий, recovery codes и использованных grants после restore; реализовать процедуру массовой инвалидизации и уведомлений.
- [ ] Для более строгих требований отдельно выбрать PITR/WAL и HA PostgreSQL, измерить failover и стоимость; реплику не считать заменой backup.

Критерий: восстановление из внешней копии и отдельного хранилища ключей проходит в пределах RPO/RTO без исходного работающего узла.

### 15. Подготовить мониторинг и реагирование к эксплуатации

Основание: metrics, JSON-логи, readiness и cleanup status уже есть; готовых dashboard/alert rules и проверенной цепочки оповещений в репозитории нет.

## Явно отложенные расширения

Не блокируют базовый single-tenant релиз; включать только по отдельному требованию с обновлением threat model и контракта:

- [ ] WebAuthn/passkeys и phishing-resistant факторы поверх проверенного MFA lifecycle.
- [ ] SCIM и плановая LDAP-синхронизация для отзыва доступа без следующего входа. Если необходим немедленный отзыв из каталога, перенести требование в P1 до выпуска.
- [ ] PAR/JAR/JARM, DPoP/mTLS и `private_key_jwt` для клиентов с повышенными требованиями; FAPI-совместимость требует отдельного профиля и conformance.
- [ ] SAML, дополнительные типы providers, динамическая регистрация клиентов и multi-tenancy — отдельные архитектурные решения.

## Нормативные источники для выполнения задач

Применимые требования проверять по [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html), включая ID Token validation и authentication context, и [OAuth 2.0 Security BCP — RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html), включая защиту authorization code и redirect flows. Версию PHPUnit выбирать по [официальной таблице поддержки](https://phpunit.de/supported-versions.html). Источники дополняют контракт PHP-приложения; новые возможности явно отражать в его документации.
